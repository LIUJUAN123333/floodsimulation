# 仿真模拟模块功能实现逻辑说明

## 1. 模块定位

仿真模拟模块是主系统中负责洪水模拟、结果转换和三维可视化播放的功能模块。该模块位于主系统导航栏的“仿真模拟”面板中，既保留了原系统的数据处理能力，又接入了优化后的洪水计算和 Mesh 渲染流程。

当前系统中，仿真模拟模块主要由三部分组成：

1. 数据处理功能
   - 格式转换
   - 粗糙度计算
   - 获取行列号
   - 地形工具

2. 洪水模拟功能
   - 上传 DEM、粗糙度、河道或溃口文件
   - 调用 C++ 后端进行洪水演进计算
   - 自动下载 TXT 和 JSON 结果压缩包

3. 洪水渲染功能
   - JSON 转 Mesh
   - 读取 Mesh 帧索引
   - 预加载 Mesh 帧
   - 在 Cesium 场景中连续播放洪水淹没过程

系统代码路径：

```text
<PROJECT_ROOT>
```

模拟计算后端路径：

```text
<PROJECT_ROOT>\FloodTest_parallel
```

## 2. 总体架构

仿真模拟模块采用前端、Vite 本地接口、Flask 数据处理后端、C++ 模拟后端协同工作的方式。

整体结构如下：

```text
Vue 前端界面
    |
    |-- 数据处理功能 --> Flask 后端 5000
    |
    |-- 洪水模拟功能 --> Vite 代理 --> C++ 模拟后端 18080
    |
    |-- JSON 转 Mesh / Mesh 读取 --> Vite 本地接口
    |
    |-- Mesh 洪水渲染 --> Cesium 三维场景
```

其中：

- Vue 前端负责用户交互、文件选择、状态显示和 Cesium 图层控制。
- Flask 后端负责原系统已有的数据处理能力，功能保持不变。
- C++ 后端负责真正的洪水数值模拟计算。
- Vite 本地接口负责 Mesh 转换、Mesh 文件夹选择、Mesh 帧读取等本地文件访问操作。
- Cesium 负责三维地球场景中的地形、影像和洪水面渲染。

## 3. 前端功能入口

仿真模拟模块的前端主要实现文件为：

```text
src/components/DataProcessingPanel.vue
```

该组件内部同时管理数据处理、模拟计算、JSON 转 Mesh 和洪水渲染状态。

主要前端函数包括：

```text
runOptimizedFloodSimulation  启动优化后的洪水模拟
waitForFloodSimulationComplete  轮询后端模拟状态
downloadApiZip  下载后端生成的 ZIP 结果
convertJsonToMesh  将 JSON 结果转换为 Mesh
loadMeshAnimationFolder  加载 Mesh 动画文件夹
readMeshFrame  读取单帧 Mesh 数据
preloadMeshFrames  预加载 Mesh 帧
renderMeshFrame  渲染指定 Mesh 帧
toggleMeshPlayback  控制 Mesh 连续播放和暂停
```

## 4. 数据处理功能逻辑

数据处理部分沿用主系统原有逻辑，主要通过 Flask 后端完成。

这部分功能包括：

1. 格式转换
   - 将用户输入的数据转换为系统需要的格式。
   - 前端把文件和参数提交给 Flask 后端。
   - 后端处理完成后返回转换结果。

2. 粗糙度计算
   - 根据输入数据计算或生成粗糙度文件。
   - 输出结果供后续洪水模拟使用。

3. 获取行列号
   - 根据地理坐标或栅格参数计算对应的行列号。
   - 常用于把实际空间位置映射到 DEM 网格中。

4. 地形工具
   - 包括地形数据相关的辅助处理。
   - 例如 TIN 构建、ASC 数据读取等。

这部分接口仍然主要访问：

```text
http://localhost:5000
```

其目的是保证主系统原来的数据处理流程不被破坏。

## 5. 洪水模拟功能逻辑

洪水模拟功能是仿真模拟模块的核心计算部分。

### 5.1 用户输入

前端要求用户选择三个主要输入文件：

```text
DEM 文件
粗糙度文件 cao
河道或溃口输入文件 river
```

同时用户需要输入 UTM 投影带号。系统会在前端校验 UTM 带号，要求其范围为：

```text
1 - 60
```

如果文件缺失或 UTM 带号不合法，前端会直接提示用户，不会向后端发起计算请求。

### 5.2 前端提交模拟任务

当前端校验通过后，会将文件封装成 `FormData`，并请求：

```text
POST /api/upload-all?utmZone=xx
```

由于 Vite 配置中设置了代理，实际会转发到：

```text
http://localhost:18080/upload-all
```

Vite 代理配置位于：

```text
vite.config.ts
```

代理规则大致为：

```text
/api/*  -->  http://localhost:18080/*
```

因此前端统一写 `/api/upload-all`，运行时由 Vite 转发给 C++ 模拟后端。

### 5.3 C++ 后端接收文件

C++ 后端接收上传文件后，会做以下处理：

1. 检查当前是否已有模拟任务正在运行。
2. 如果已有任务运行，则返回 409，避免多个任务同时写同一个结果目录。
3. 清理旧的上传目录和旧的模拟目录。
4. 创建新的上传目录和模拟目录。
5. 校验 UTM 带号。
6. 读取上传文件。
7. 将文件保存为固定名称：

```text
dem.asc
cao.asc
InputRiver.dat
```

8. 将这三个文件复制到模拟工作目录：

```text
../Data_dx_5m
```

这一步的作用是适配原 C++ 模型的输入文件命名方式。模型内部固定读取 `dem.asc`、`cao.asc` 和 `InputRiver.dat`，因此前端上传的文件最终会被统一整理成这三个名称。

### 5.4 异步启动模拟

C++ 后端不会在 HTTP 请求里同步完成全部模拟，而是启动一个后台线程执行：

```text
runFloodSimulation(...)
```

然后立即返回：

```json
{
  "message": "Simulation task started.",
  "statusUrl": "/simulation-status"
}
```

这样前端不会因为模拟时间过长而卡死。

前端收到响应后，进入轮询状态，不断请求：

```text
GET /api/simulation-status
```

实际对应：

```text
GET http://localhost:18080/simulation-status
```

后端状态主要包括：

```text
starting  准备启动
running   正在计算
finished  计算完成
failed    计算失败
```

## 6. 洪水数值模拟原理

后端模拟程序本质上是一个基于规则栅格的二维洪水演进模型。

### 6.1 栅格计算单元

系统首先读取 DEM 文件，将研究区域拆分为规则网格。每一个网格单元都可以理解为一个小的计算单元。

每个单元中主要保存以下信息：

```text
地形高程
水深
水面高程
粗糙度
东西方向通量
南北方向通量
边界状态
是否为入流点或溃口点
```

其中：

```text
水面高程 = 地形高程 + 水深
```

洪水是否向周围扩散，主要取决于相邻网格之间的水面高程差。

### 6.2 DEM 的作用

DEM 文件提供地形高程。地势越低的区域越容易积水，地势越高的区域则会阻挡或改变洪水流向。

模型读取 DEM 后，会建立二维网格数组，并把每个格子的地形高程写入对应单元。

如果某些格子属于无效区域或边界区域，模型会将其设置为边界状态，防止水流错误地流出计算区域或进入无效区域。

### 6.3 粗糙度的作用

粗糙度文件 `cao.asc` 用于表示地表阻力。

粗糙度越大，表示地表越粗糙，水流受到的阻力越强，流速会变慢。粗糙度越小，水流越容易通过。

在计算相邻网格之间的流量时，模型会把粗糙度作为摩阻因素参与计算。

### 6.4 河道或溃口输入的作用

`InputRiver.dat` 用于描述洪水输入位置，例如河道入流点、溃口点或源点。

模型初始化时会读取该文件，将对应网格标记为源点。模拟开始后，这些源点会向周围网格注入水量，从而形成洪水扩散过程。

### 6.5 水流计算原理

每一个时间步内，模型会遍历所有有效网格，计算该网格与周围网格之间的水位差。

基本思想是：

```text
水面高程高的格子，会向水面高程低的格子流动。
```

例如某个格子的水面高程高于右侧格子，则会产生向右的流量；如果低于右侧格子，则右侧格子可能向当前格子回流。

水流强弱主要受以下因素影响：

```text
水位差
网格距离
地形坡度
水深
粗糙度
重力加速度
时间步长
```

每个时间步的大致过程为：

```text
计算当前入流或溃口流量
        ↓
遍历所有有效网格
        ↓
计算相邻网格之间的水面高程差
        ↓
根据坡降和粗糙度计算通量
        ↓
限制异常通量，保证计算稳定
        ↓
更新每个网格的水深和水面高程
        ↓
推进到下一个时间步
```

### 6.6 并行计算

洪水模拟需要对大量网格重复计算，如果单线程运行会比较慢。

后端模型使用 OpenMP 对网格循环进行并行化处理，使多个 CPU 线程同时计算不同区域的网格。

并行计算主要用于：

```text
通量计算
水深更新
网格状态遍历
```

这样可以提升大范围洪水模拟的计算效率。

## 7. 模拟结果输出逻辑

模型运行过程中，会按一定间隔输出洪水结果。

每一帧结果最初会输出为 TXT 或 ASC 格式。该格式本质上仍然是规则网格，每个格子对应一个水深值。

输出流程如下：

```text
模型计算若干时间步
        ↓
导出当前时刻水深栅格 TXT
        ↓
将 TXT 转换为 JSON
        ↓
继续计算下一时刻
```

模拟结束后，后端会把所有 TXT 和 JSON 结果分别压缩为：

```text
flood_txt.zip
flood_json.zip
```

前端在检测到状态为 `finished` 后，会自动下载这两个压缩包。

## 8. TXT 转 JSON 原理

模型原始输出是规则网格 TXT 文件，其中包含：

```text
ncols
nrows
xllcorner
yllcorner
cellsize
NODATA_value
每个网格的水深值
```

但是前端渲染洪水时，并不需要所有网格。没有水的区域不需要绘制，否则会造成大量无效数据。

因此后端在转换 JSON 时，会只保留：

```text
水深值 > 0 的网格点
```

对于每个有效点，后端会计算其网格中心坐标，并将 UTM 坐标转换为 WGS84 经纬度。

最终生成的 JSON 结构大致为：

```json
{
  "min": 0.001,
  "max": 8.19,
  "points": [
    {
      "x": 106.123456,
      "y": 29.123456,
      "value": 1.25
    }
  ]
}
```

字段含义：

```text
min    当前帧最小水深
max    当前帧最大水深
x      经度
y      纬度
value  水深
```

这样处理后，JSON 文件比完整栅格更适合前端可视化。

## 9. JSON 转 Mesh 功能逻辑

原始 JSON 是点数据，只记录了每个水深点的位置和值。点数据本身不能形成连续水面，因此需要进一步转换为 Mesh。

JSON 转 Mesh 功能由 Vite 本地接口实现，主要接口是：

```text
POST /api/build-mesh
```

该接口不是转发给 C++ 后端，而是在 Vite 进程中直接处理。

实现位置：

```text
vite.config.ts
```

前端传入：

```json
{
  "sourceDir": "JSON 源文件夹",
  "outputDir": "Mesh 输出文件夹"
}
```

Vite 接口收到请求后，会启动 Node 脚本：

```text
backend/build-mesh-cache.cjs
```

该脚本完成以下工作：

1. 遍历 JSON 源文件夹。
2. 读取每一帧 JSON 洪水点数据。
3. 提取经纬度和水深。
4. 将点数据构建为三角网。
5. 输出对应的 `.mesh.json` 文件。
6. 生成统一的 `index.json` 索引文件。

转换后的 Mesh 文件主要包含：

```text
positions      点坐标数组，经纬度交替存储
values         每个点对应的水深
triangles      三角形顶点索引
stats          当前帧统计信息
pointCount     点数量
triangleCount  三角形数量
```

`index.json` 中记录所有帧的顺序、文件名和统计信息，前端加载 Mesh 动画时会优先读取该文件。

## 10. 为什么要转 Mesh

直接播放原始 JSON 点数据会有几个问题：

1. 每一帧都需要重新解析大量点。
2. 每一帧都需要重新构建三角形。
3. 前端计算压力大，播放时容易卡顿。
4. 点数据无法天然形成连续水面。

转换为 Mesh 后，三角网已经提前计算好。播放时前端只需要：

```text
读取 Mesh
创建 Cesium Primitive
替换上一帧 Primitive
```

这样可以显著减少播放过程中的计算量，使洪水动画更加流畅。

## 11. Mesh 文件读取逻辑

洪水渲染时，用户选择 Mesh 文件夹后，前端调用：

```text
POST /api/mesh-index
```

Vite 本地接口读取该文件夹中的：

```text
index.json
```

然后返回所有帧信息。

前端拿到帧列表后，会：

1. 按帧序号排序。
2. 默认渲染第一帧。
3. 自动定位到洪水区域。
4. 后台开始预加载所有 Mesh 帧。

单帧 Mesh 读取接口为：

```text
GET /api/mesh-frame?folder=xxx&name=xxx.mesh.json
```

该接口会读取指定的 `.mesh.json` 文件并返回给前端。

## 12. Mesh 预加载逻辑

为了保证播放流畅，系统增加了前端缓存机制。

前端读取 Mesh 文件夹后，会后台执行：

```text
preloadMeshFrames
```

预加载逻辑是：

```text
读取 index.json
        ↓
获取所有 Mesh 帧文件名
        ↓
并发读取多帧 Mesh
        ↓
存入前端 Map 缓存
        ↓
播放时优先从缓存读取
```

当前预加载会控制并发数量，避免一次性请求过多文件导致浏览器或本地服务压力过大。

播放时，如果检测到所有帧尚未缓存完成，系统会先等待预加载完成，再开始连续播放。

## 13. Cesium 洪水渲染原理

Mesh 洪水面最终通过 Cesium 的 `Primitive` 绘制。

渲染实现主要在：

```text
V0226C/V0226C/src/js/DrawTriangleMesh.js
```

渲染时，系统会遍历 Mesh 中的点，将每个点转换成 Cesium 三维坐标。

每个点的高度计算逻辑可以理解为：

```text
最终高度 = 地形高度 + 水深 × 高度比例 + 表面偏移
```

其中：

```text
地形高度    来自 Cesium 地形采样，未开启真实地形时可视为 0
水深        Mesh values 中的值
高度比例    用户在界面中调整的高度比例
表面偏移    一个很小的偏移值，用于避免洪水面和地形重叠闪烁
```

### 13.1 地形开启时

如果系统开启真实地形，前端会对 Mesh 点进行地形采样。

采样过程是：

```text
经纬度点
    ↓
Cesium.sampleTerrainMostDetailed
    ↓
得到地形高度
    ↓
洪水面叠加到地形之上
```

这种方式可以让洪水面更贴合实际地形。

### 13.2 地形关闭时

如果关闭真实地形，系统使用 Cesium 默认椭球或平滑表面。

此时洪水面不再采样真实地形，渲染速度通常更快，也更不容易受到地形瓦片加载状态影响。

## 14. 洪水颜色映射原理

洪水面颜色由水深决定。

系统会根据当前帧的最小水深和最大水深，将每个点的水深归一化到一个范围内。

逻辑大致为：

```text
水深较小  -> 浅色
水深较大  -> 深色
```

用户可以在界面中切换不同颜色方案，例如水蓝色方案等。

颜色和透明度会写入 Cesium Geometry 的顶点颜色中，然后通过 `PerInstanceColorAppearance` 显示出来。

## 15. 洪水动画播放原理

洪水动画不是视频，而是多帧 Mesh 数据的连续切换。

播放过程如下：

```text
读取第 1 帧 Mesh
        ↓
创建洪水 Primitive
        ↓
加入 Cesium 场景
        ↓
等待一小段时间
        ↓
移除上一帧 Primitive
        ↓
读取第 2 帧 Mesh
        ↓
创建新的 Primitive
        ↓
继续循环
```

用户点击“连续播放”后，前端会根据播放速度设置定时器。每次定时器触发，就渲染下一帧。

用户点击“暂停播放”后，系统清除定时器，保留当前帧画面。

用户点击“清除图层”后，系统会从 Cesium 场景中移除当前洪水 Primitive。

## 16. 前端状态显示逻辑

洪水渲染面板会显示当前 Mesh 数据状态，包括：

```text
当前帧
点数
三角面数量
水深范围
当前文件名
渲染状态提示
```

这些信息主要来自：

```text
index.json
*.mesh.json
```

当用户调整透明度、高度比例或颜色方案时，前端会重新渲染当前帧，使参数立即生效。

## 17. 端口和服务依赖

仿真模拟模块完整运行时，通常需要以下服务：

```text
Vite 前端服务        5174 或实际启动端口
Flask 数据处理后端   5000
C++ 模拟计算后端     18080
```

其中：

- 数据处理功能依赖 Flask 5000。
- 洪水模拟功能依赖 C++ 18080。
- JSON 转 Mesh 和 Mesh 读取依赖 Vite 本地接口。
- Cesium 渲染运行在浏览器前端。

## 18. 完整业务流程

完整流程可以概括为：

```text
准备 DEM、粗糙度、河道文件
        ↓
在前端选择文件并输入 UTM 带号
        ↓
前端提交到 /api/upload-all
        ↓
Vite 代理到 C++ 后端 18080
        ↓
C++ 后端保存输入文件
        ↓
启动洪水数值模拟
        ↓
按时间步输出 TXT 水深结果
        ↓
将 TXT 转换为 WGS84 经纬度 JSON
        ↓
压缩 TXT 和 JSON 结果
        ↓
前端自动下载结果 ZIP
        ↓
用户选择 JSON 文件夹和 Mesh 输出文件夹
        ↓
Vite 本地接口调用 Node 脚本生成 Mesh
        ↓
用户选择 Mesh 文件夹
        ↓
前端读取 index.json
        ↓
预加载所有 Mesh 帧
        ↓
Cesium 中连续播放洪水淹没过程
```

## 19. 当前设计的优点

当前实现方式的主要优点是：

1. 原有数据处理功能保持不变，降低对主系统其他功能的影响。
2. 洪水模拟计算交给 C++ 后端，适合执行高强度数值计算。
3. 前端通过轮询状态获取计算进度，避免长时间 HTTP 阻塞。
4. JSON 转 Mesh 提前完成三角网构建，减少播放时的实时计算。
5. Mesh 帧预加载提升动画流畅度。
6. Vite 本地接口直接读取本地 Mesh 文件，速度较快。
7. Cesium Primitive 渲染适合显示大量三角形洪水面。

## 20. 测试关注点

测试仿真模拟模块时，可以按以下顺序检查：

1. 数据处理功能是否仍能正常调用 Flask 5000。
2. C++ 后端 18080 是否已经启动。
3. 模拟计算是否能成功上传 DEM、cao 和 river 文件。
4. `/api/simulation-status` 是否能返回运行状态。
5. 模拟完成后是否能下载 TXT 和 JSON 压缩包。
6. JSON 转 Mesh 是否能生成 `index.json` 和 `.mesh.json`。
7. Mesh 文件夹是否能被成功加载。
8. 第一帧洪水是否能正常显示。
9. 预加载完成后连续播放是否流畅。
10. 开启和关闭地形时，洪水面是否都能显示。
11. 透明度、高度比例、颜色方案、播放速度等控制项是否生效。

## 21. 简要总结

仿真模拟模块的核心思想是：

```text
用 C++ 后端完成洪水数值模拟，
用 JSON 保存每个时刻的水深点数据，
用 Node 脚本提前转换为 Mesh 三角网，
用 Cesium 在三维场景中逐帧播放 Mesh，
最终形成动态洪水淹没可视化效果。
```

该模块把高强度计算、数据预处理和三维渲染拆分到不同环节中处理，既保留了原系统的数据处理功能，又提升了洪水结果播放的流畅性和可视化效果。
